# PokerCalc

Веб-приложение: свой аналог **Flopzilla** с расширенным функционалом. Всё считается в браузере, бэкенда нет.

Референс по UI и фичам — софт «Greenline Junior» (тёмная тема, матрица 13×13, разбор борда по категориям, эквити, heatmap).

Ключевые фичи, ради которых проект и строится: **эквити range vs range** и **range morphing** (сужение диапазона по улицам).

## Команды

```bash
npm run dev        # дев-сервер → http://localhost:5173
npm test           # vitest
npm run typecheck  # tsc без сборки
npm run build      # прод-сборка
```

Терминал с `npm run dev` держать открытым — это и есть сервер.

## Стек

Vite 6 + React 19 + TypeScript + Tailwind v4 + Zustand. Тесты — Vitest. Эквити считается в Web Worker.

### Модель диапазона

`Range` — `Float32Array` на 1326 комбо, вес каждого 0..1. Мутируется на месте, поэтому в сторе есть счётчик `rev`, который инкрементится при любом изменении — на него подписаны компоненты, иначе React не перерисует.

Блокеры (карты борда и heroCards) — bigint-маска; `liveCombos(mask)` и `totalCombos(mask)` отсекают пересекающиеся комбо.

### Эквити

`computeEquity(a, b, board, opts)` — гибрид: если пространство раскладов маленькое (обычно тёрн/ривер), идёт точный перебор, иначе Monte Carlo. Валидировано по эталонам: AA vs KK ≈ 82%, AKs vs QQ ≈ 46%.

Hero-сторона в UI: если заданы **обе** карты в слотах Hero — считается эта конкретная рука; иначе берётся диапазон Hero.

## Префлоп-пресеты (Green Charts 2024, Greenline Poker)

Источник — PDF `~/Downloads/GreenCharts2024_01.pdf`, 12 страниц, кэш NL2–NL200. Диапазоны **оцифрованы скриптом**, не набраны руками.

### Модель — по действиям

```ts
RangePreset {
  actions: PresetAction[]   // kind: "raise" | "call"
}
PresetAction {
  always: string[], situational: string[],
  threeQuarter?: string[], quarter?: string[],   // только Defense vs 3Bet
  color?: ActionColor, label: string,            // для легенды и раскраски
}
```

- `always` → вес **1.0** (в чарте сплошной цвет)
- `situational` → вес **0.5**
- `threeQuarter` / `quarter` → **0.75** / **0.25**

Полсотни процентов — не выдумка: подписанные в PDF проценты сходятся **только** по формуле `always + situational/2`. Это проверяется тестом. Четверти понадобились только на стр. 10–11, где ячейка делится не пополам.

Одному `kind: "raise"` могут отвечать **два** действия с разным `color` — так в Defense vs 3Bet разделены «4бет-фолд» (красный) и «4бет-пуш» (фиолетовый). На вес и на фильтр действия это не влияет, нужно только для легенды.

`store.applyPreset(id, includeSituational, actionKind?)` — без `actionKind` применяются все действия пресета, и руки, лежащие в двух действиях по половине, складываются в полный вес.

### Семантика цветов зависит от типа чарта — легенду смотреть каждый раз

| Страница | Чарт | Красный | Жёлтый / Зелёный |
|---|---|---|---|
| 4 | RFI | открываем всегда | жёлтый — ситуативно |
| 6 | SB Defense | 3бетим всегда | жёлтый — 3бетим в подходящих оппонентов |
| 7 | BB Defense | 3бетим | **зелёный — коллируем** |
| 5 | Isolate | открываем изолэйтом | **зелёный — доставляем 0.5bb на SB** |
| 8 | Blinds vs 4bet | — | зелёный — коллируем 4бет, жёлтый — коллим кроме пассивных, **фиолетовый — 5бет-пуш** |

На SB — чистый 3бет-или-фолд, флэтов нет. На BB есть и колл, поэтому там два действия.

**Составные ячейки:** в BB-чартах ячейка может быть закрашена наполовину двумя цветами — смешанная стратегия «половину раздач 3бет, половину колл», всегда ровно 50/50. Такие руки попадают в `situational` **обоих** действий.

### Что уже оцифровано

- `rfi.ts` — открытие. Сайзинг CO/BU 2.5bb, остальные 3bb. **Все пять позиций перенесены со скриншотов трёхцветных чартов** (другой источник, не PDF).
  - Легенда трёхцветных: красный — открываем всегда (вес 1), жёлтый — в мягких ситуациях (0.5), **зелёный — только когда на блайндах супер-ВИП (0.25)**. Зелёное — отдельное действие того же `kind: "raise"` с `color: "green"`, как «4бет-фолд»/«4бет-пуш» в `defenseVs3bet.ts`; иначе `YELLOW_PARTIAL_GROUPS` перекрасил бы его в жёлтый (в `store.ts` для этого стоит `yellowPartial && !action.color`).
  - Ширины: UTG 14.4%, MP 16.6%, CO 26.2%, BU 43.4%, SB 58.9%. Подпись у этих чартов — **полоса** («MP 14-22%», «CO 23-29%», «BU 37-45», «SB 45 и выше»), поэтому тест проверяет попадание в полосу, а не совпадение с точкой. На SB зелёного больше, чем всего остального: красный+жёлтый дают 46.9% — те самые «45 и выше», — а вместе с зелёным выходит 58.9%, и в чарте не остаётся ни одной пустой ячейки (все 169 рук чем-то покрашены).
  - Нижний ряд матрицы на скриншотах лежит на затемнённой плашке: 22 там выглядит тёмно-зелёной/тёмно-жёлтой, но это тот же цвет, что у 44/33.
- `iso.ts` — стр. 5: изолэйт после лимпа, MP 11% / CO 14% / BU 20% / SB 12% / BB 14%. Генерируется `tools/gen_iso.py`.
- `blinds4bet.ts` — стр. 8: защита блайндов от 4бета, vs UTG / MP / CO / BU (2.5 и 3bb) и BB vs SB. Генерируется `tools/gen_blinds4bet.py`.
- `sbDefense.ts` — стр. 6: vs UTG / MP / CO / BU
- `bbDefense.ts` — стр. 7: vs UTG / MP / CO / SB, плюс vs BU отдельно для сайзингов 2.5bb и 3bb
- `threeBetIP.ts` — стр. 9: 3бет в позиции vs опен 15% / 18% / 26%
- `defenseVs3bet.ts` — стр. 10 и 11: защита от 3бета в позиции (6/8/10/12/14%) и без позиции (8/10/12/18%)

**Осторожно с процентами.** `extract_charts.py` печатает `total` как долю **закрашенной площади** чарта (жёлтый считается за целую руку), а эффективная ширина диапазона в приложении — это `always + situational/2`. Для RFI UTG это 16.0% против 14.1%. Сверять надо с эффективной: её считает `presetWidthPct()` в `presets/tree.ts`, она же показывается под веткой событий.

### Осталось оцифровать

Все страницы с диапазонами оцифрованы.

### Как оцифровывать (процедура)

Требуется `pip install PyMuPDF numpy scipy`.

1. `python tools/extract_charts.py <номер_страницы>` — для чартов без составных ячеек.
   `python tools/extract_charts_mixed.py <номер_страницы>` — если в чарте есть ячейки, закрашенные двумя цветами (считает доли пикселей).
2. Посмотреть легенду страницы: отрендерить верхнюю полосу (`clip` в fitz) — от неё зависит смысл цветов и структура действий.
3. Сетки сортируются «сверху вниз, слева направо»; подписи (какая позиция против какой) скрипт не знает — берутся из легенды/скриншота.
4. **TS-файл генерировать скриптом на Python**, а не набирать руками. При ручном переносе уже была поймана реальная опечатка (дубль `A6o` в RFI BU).
5. Если всё же правил руками — сверить регуляркой с извлечённым JSON перед коммитом.

### Изолэйт (стр. 5)

Легенда: красный — открытие изолэйтом, зелёный — «доставляем 0,5bb на SB, если до нас уже были лимперы». Зелёный есть **только** в чарте SB: доставить блайнд может лишь тот, кто его уже наполовину поставил. UTG в чарте нет — до него лимпить некому.

Сайзинг: в позиции 4bb + 1bb за каждого лимпера, без позиции 5bb + 1bb. По этому признаку CO/BU считаются в позиции, MP/SB/BB — вне.

Составные ячейки здесь ровно 50/50 и это **настоящий раздел ячейки**, а не другой цвет чернил, как жёлтый в RFI, — поэтому ISO не входит в `YELLOW_PARTIAL_GROUPS` в `store.ts`. Подписанный на чарте процент относится к **красному** диапазону: у SB это 12% при зелёных 17.9% сверху.

Проверка сходимости при оцифровке (доли пикселей → вес 0.5 на половинках): MP 10.7 против подписанных 11, CO 14.1 против 14, BU 20.1 против 20, SB-изо 12.1 против 12, BB 13.7 против 14.

Половинные ячейки читаются как 0.41–0.54, а не ровно 0.5: тёмный текст ярлыка внутри ячейки съедает часть пикселей, сильнее всего в offsuit-ячейках с тремя символами. Порог в `gen_iso.py` поэтому низкий (0.06), но заведомо выше шума антиалиасинга.

### Защита блайндов от 4бета (стр. 8)

Легенда: зелёный — коллируем 4бет, жёлтый — «фолдим на 4бет от пассивных оппов, в остальных случаях коллим», фиолетовый — 5бет-пуш (олл-ин).

Жёлтый здесь — это **ситуативный колл**, а не отдельное решение, поэтому он вынесен в отдельное действие того же `kind: "call"` со своим цветом. На вес это не влияет (`handWeights` складывает действия одного kind), зато матрица красится цветами оригинала. Тот же приём, что с «4бет-фолд» / «4бет-пуш» в `defenseVs3bet.ts`. Включить группу в `YELLOW_PARTIAL_GROUPS` было нельзя: там же есть настоящие разделы ячейки зелёный/фиолетовый, и они бы стали жёлтыми.

Составные ячейки делятся не только пополам: у 99/88 против BU 2.5bb и TT против BU 3bb на пуш приходится **четверть** — как на стр. 10–11.

**Процентов в заголовках чартов на этой странице нет**, поэтому обычная сверка ширины невозможна. Вместо неё в тестах структурный инвариант: защищаться от 4бета можно только той рукой, которой ты и 3бетнул, — весь диапазон чарта обязан умещаться в `sb3bet-vs-*` ∪ `bbdef-vs-*` для того же опенера. Плюс проверка порядка ширины: против SB защищаемся шире, чем против CO, и тем более UTG.

Эффективные ширины (колл / пуш / всего): vs UTG 1.5/0.8/2.3, vs MP 1.7/1.1/2.7, vs CO 1.5/2.3/3.8, vs BU 2.5bb 3.3/3.6/6.9, vs BU 3bb 3.4/2.8/6.2, BB vs SB 4.6/4.4/9.0.

Осторожно при перегенерации: в `width_pct` жёлтый обязан идти весом 0.5. Если посчитать его целым, печатаемая ширина разойдётся с тем, что показывает приложение, — на этом я один раз уже споткнулся.

AA против 4бета **не всегда пуш**: у всех чартов страницы половина AA уходит в колл, чтобы не остаться без сильных рук в коллирующем диапазоне. Из-за этого пришлось разделить общий тест «AA разыгрывается агрессивно» на два: «AA никогда не фолдится» (жёсткий) и «пуш не реже колла» (с порогом).

## MTT-чарты (FF START)

Источник — пак картинок FF START (ffstart.online), 8 страниц PNG в `charts/mtt/`. Оцифрованы скриптом, руками не набирались.

```bash
python tools/extract_ffstart.py --debug charts/mtt/*.png   # PNG → charts/mtt/ffstart.json
python tools/gen_mtt.py                                    # JSON → src/presets/mtt/*.ts
```

`--debug` кладёт рядом `<имя>.debug.png` с обведёнными сетками и разметкой ячеек — глазами проверить границы дешевле, чем ловить сдвиг на ряд по разъехавшимся процентам.

### Чем эти чарты отличаются от кэшевых

**Они бинарные.** Рука играется ровно одним действием, долей и составных ячеек нет — всё уходит в `always`, `situational`/`mixed` остаются пустыми. Это закреплено тестом: появление дробного веса означает, что цвет ячейки прочитался неоднозначно.

**Глубина стека — часть спота, а не фон.** На 25bb+ открываем рейзом 2bb, на 10-14bb уже только пуш-фолд, против опена на 40bb+ коллируем и 3бетим, а на 16-22bb ставим олл-ин.

Поэтому стек вынесен **в конфиг над деревом** (как в GTO Wizard), а не в шаг внутри него: `MTT_STACKS` в `mtt/tree.ts` — пять глубин, у каждой **своё дерево**. Сначала выбираешь стек, дальше видишь только те линии, которые на нём существуют.

Отсюда главное правило файла: **дерево не показывает линию, под которую в паке нет чарта.** На 16-22bb нет своего опена, на 25-40bb — игры против опена. Подставить туда соседнюю глубину было бы незаметным враньём, поэтому вместо этого в `note` конфига честно написано, чего на этом стеке нет. Обратная опасность — чарт, до которого не ведёт ни один путь: это ловит тест «каждый MTT-чарт достижим хотя бы на одной глубине».

Конфиги живут в `FORMATS` (`presets/index.ts`): у кэша он один (100bb) и селектор скрыт, у MTT их пять. Порядок — от глубокого к короткому, потому что первый конфиг дефолтный, а полное дерево полезнее как точка входа, чем пуш-фолд на девяти блайндах.

**Позиции — как в оригинале:** EP+1 / EP+2 / MP / HJ / CO / BU. На 8-max первая позиция — EP+1, на 6-max — MP. Часть чартов задана **группой** позиций («ранние», «поздние»), и так группой и остаётся: раскладывать их по конкретным местам самим — выдумывать данные.

### Сверка оцифровки

Главный тест — подписанный на чарте процент против фактической ширины. Он относится к **агрессивной** линии (опен / изолейт / пуш), пассивная на чартах не подписана. Допуск **1.5 п.п.**, и это не небрежность: на двух чартах (изолейт CO 25.5 против подписанных 26, пуш MP 24.1 против 23) расходится сама подпись — ячейки там сверены с картинкой поштучно. Порог всё равно ловит сдвиг на ряд и перепутанные местами чарты.

Плюс структурные инварианты, которые все выполняются на извлечённых данных:

- RFI **вложены**: каждая следующая позиция только добавляет руки;
- защита от 3бета целиком лежит **внутри опена того же места** (межстраничная сверка стр. 1 и 4) — включая серые «фолд»-ячейки, что и подтверждает, что серый там означает «открылись, но сдаём»;
- пуш на 0-9bb ⊇ пуш на 10-14bb для каждой позиции;
- BB защищается тем шире, чем позднее опенер, при **одинаковом** 3бете на всех трёх чартах (так в оригинале).

### Гочи извлечения

- Чарт «Против 2+ лимперов» лежит на **бежевой плашке**, и его заголовок по плотности не отличается от рядов ячеек — бокс затягивал подпись и вся сетка съезжала на ряд. Лечится приведением бокса к квадрату с прижатием к нижнему краю: матрица 13×13 квадратная, а заголовок всегда сверху.
- Чарт «BB против 1 лимпера» тоже на плашке, поэтому его фолд-ячейки читаются как `grey`, а не `white`. На результат не влияет — обе краски означают «не играем».
- Отладочные оверлеи пишутся рядом с исходниками и попадают под `charts/mtt/*.png`; в скрипте стоит фильтр по `.debug.`, иначе вторым проходом они переписывают `ffstart.json` своими копиями.
- Консоль Windows по умолчанию cp1251 и падает на стрелках в выводе — оба скрипта переключают stdout на utf-8.
- Ре-экспорт вида `import { X } from "./m"; export { X };` **ломает Vite**: tsc и vitest его проглатывают, а браузер получает модуль, где имя не определено, и приложение падает на загрузке. Писать `export { X } from "./m"` (импорт при этом можно оставить, если X нужен в самом файле). Поймано только в консоли браузера — ни typecheck, ни тесты этого не видят.

## Гочи

- **vitest тянет свою вложенную копию vite** → конфликт типов. Поэтому конфиги разделены: `vite.config.ts` (плагины, без `test`) и отдельный `vitest.config.ts` (только `test`).
- **localhost на Windows** может резолвиться в IPv6 (`::1`), а Vite слушать IPv4 → `ERR_CONNECTION_REFUSED`. В `vite.config.ts` стоит `server.host: true` и фиксированный порт 5173.
- Извлечение чартов: заголовок чарта слипается с сеткой при дилатации маски — границы берутся по **span** строк/столбцов с плотностью > 0.6, а не по «самому длинному непрерывному участку» (последний рвётся на 13 кусков из-за белых зазоров между рядами ячеек).
- Сетки одного ряда могут отличаться по `y` на пиксель, поэтому сортировка идёт по `(round(y/400), x)`.

## Цвета матрицы

Матрица по умолчанию **одноцветная** (`src/ui/colors.ts`): один нейтральный
серый акцент на все три зоны, заливка ячейки слева = вес руки. Раньше оттенок
кодировал тип руки (пары зелёные, suited синие, offsuit оранжевые), но тогда
цвет нёс сразу два смысла и спорил с раскраской по действиям чарта. Теперь
оттенок свободен под чарт, а дефолт говорит только о весе — легенда типов рук
под матрицей за ненадобностью убрана.

Поэтому **«цвета пресета» включены по умолчанию** (`presetColorMode: true`):
применил чарт — сразу видишь его красный/жёлтый/зелёный, как на оригинале.

Heatmap (тумблер в боковой панели) перекрашивает руки диапазона по силе на борде: красный слабо → зелёный сильно.

**Цвета пресета** (тумблер там же) красит руки по действию, как в оригинальных чартах: зелёный — колл, красный — 3бет / 4бет-фолд, фиолетовый — 4бет-пуш, жёлтый — ситуативные руки в RFI/SB/3бет-IP. В MTT добавляются оранжевый (обычный изолейт, в отличие от крупного — красного) и розовый (олл-ин). Составная ячейка заливается сегментами пропорционально весам. Раскладка живёт в `store.presetView`, подписи легенды — в `store.presetLegend` (берутся из `action.label`, поэтому легенда всегда соответствует текущему чарту). Любая ручная правка диапазона обнуляет и то, и другое — раскраска по действиям после неё уже не имеет смысла.

## Ветка событий (`ui/ActionTree.tsx`, `presets/tree.ts`)

Спот собирается по шагам, как action tree в GTO Wizard: **кто открыл → кто и как ответил → как опенер ответил на 3бет**. Плоских рядов кнопок по группам больше нет.

- Кто IP, а кто OOP, выводится строго из мест за столом: 3бет от CO/BU оставляет опенера **вне** позиции, 3бет от блайндов — **в** позиции, а BB против опена SB сам оказывается в позиции (это и есть чарт «OOP vs 3bet 18% (SB vs BB)»).
- Чарты, заданные **процентом** (3бет IP, защита от 3бета), по позиции **не** подставляются: проценты в них — ширина диапазона соперника, и с нашими позиционными диапазонами они совпадают лишь приблизительно. Такой шаг даёт явный выбор %, а фактическая ширина показана подсказкой.
- `presetForPath(path)` — какой чарт и фильтр действия соответствуют пути. Тест обходит всё дерево и проверяет, что каждый `presetId` существует и в чарте есть указанное действие.

## Тренажёр (`ui/Trainer.tsx`, `presets/quiz.ts`)

Вкладка «Тренажёр» в шапке. Показывает конкретную руку в конкретном споте, игрок выбирает действие, дальше — разбор с долями по чарту.

**Очевидные вопросы не задаются.** Спрашивать «открываем ли 72o с UTG» бессмысленно. В выборку (`interestingHands`) попадают только:

1. **смешанные** руки — чарт играет их частично (0.25/0.5/0.75), правильных ответов несколько;
2. **пограничные** — соседняя по сетке рука играется иначе (A5s открываем, A4s уже нет → обе в тесте).

Всё, что окружено такими же руками с тем же действием, отсеивается: и мусор, и премиум в середине своей зоны. Из 169 ярлыков остаётся ~55–90 на спот. Это закреплено тестами (`72o`/`AA` для RFI UTG в выборку попадать не должны).

На бинарных MTT-чартах смешанных рук нет вообще, и выборка держится **только** на границах. Она всё равно осмысленная: от 6 рук на узком рестил-чарте «блайнды против ранней» (он и сам всего 6%) до ~110 на защите BB. Тест требует минимум 4 руки на спот.

Соседство считается по сетке 13×13, но переходы пара↔непара соседством **не** считаются (у них разная природа), а `suited↔offsuit` той же пары рангов — считается: AJs играем, AJo нет — полезная граница.

Ответ верен, если чарт играет руку так **хоть какую-то долю времени** (`isCorrect`): на смешанной руке верны оба действия, фолд — нет.

**Отказ сыграть руку — не всегда фолд.** На BB в лимпед-поте фолда нет вовсе: блайнд уже поставлен, и не изолировать можно только чеком. Тренажёр же предлагал «Фолд» и на BB — невозможное действие (поймано на K3s против лимпа SB). Теперь у таких спотов кнопка подписана «Чек» (`declinesByCheck`), и за столом это чек, а не сброс карт. Та же поправка давно стоит в разборе истории рук (`checkDeclines` в `hh/deviations.ts`) — тренажёр от неё отстал.

Действия одного `kind` при проверке складываются: «4бет-фолд» и «4бет-пуш» для игрока — один ответ «4бет», разделены они только ради цвета в легенде.

**На пуш-фолде есть заведомо неверный ответ.** На 0-14bb и на рестиле 16-22bb пак рейзов не знает вовсе — либо олл-ин, либо фолд, — и спот сводился к двум кнопкам, где «олл-ин» угадывается даже с рукой, которой в чарте нет. Поэтому там добавлен ответ `smallraise` («Рейз 2bb», на рестиле «3бет 5bb») с весом всегда 0. Это единственный ответ, которому не соответствует действие чарта; тест проверяет и что он есть на пуш-спотах, и что его нет больше нигде.

**Нерешённое: колл на рестиле 16-22bb.** В споте «блайнды против ранней» (стек 16-22bb, опен 2bb) тренажёр предлагает только фолд / рейз 5bb / 3бет-пуш — колла нет, потому что чарт стр. 9 задаёт **только** пуш-диапазон. На BB, закрывающем действие против опена в 2bb, это выглядит неполно.

Там же вылезает причуда самого пака, а не оцифровки: чарт «на блайндах против ранней» (6%) местами **уже**, чем «ранняя против ранней» (5.4%) — AJs пушится с ранней, но не с блайнда, зато на блайнде добавлены 88/77. Сверено с исходной картинкой поштучно: в пакете ячейка AJs там белая. Так что «пуш с AJs — ошибка» тренажёр показывает верно, но объяснить это игроку нечем.

Что делать — не решено: либо добавить колл заведомо неверным ответом (как «Рейз 2bb» на пуш-фолде), либо оставить как есть, либо искать источник для коллирующего диапазона на этой глубине.

**Подсказка о границе.** При неверном ответе показывается, докуда тянется каждое действие (`actionEdges`): «Граница среди Axs: колл — до A2s, 3бет — до A4s (частично)».

**Кэш и MTT не смешиваются в одном прогоне.** Сверху переключатель формата, под ним — группы спотов внутри выбранного (`TRAINER_SECTIONS` в `presets/quiz.ts`). Иначе по одному лишь тексту спота непонятно, по какому источнику отвечать: сайзинги и глубины стека разные. Счёт при смене формата не сбрасывается — он про игрока, а не про чарты.

Разбиение живёт в `quiz.ts`, а не в `Trainer.tsx`, из-за реального бага: MTT-чарты оцифровались и попали в `QUIZ_SPOTS`, но список групп в UI остался старым, и до них нельзя было добраться ни одной кнопкой. Теперь тест сверяет объединение секций со всеми группами, какие есть в `ALL_PRESETS`, — в обе стороны.

Граница считается по **ряду** руки в матрице (`handFamily`) — те же старшая карта и тип: для AJs это все Axs, для AJo — Axo, для 77 — все пары. Именно так чарты и запоминаются («Axs открываем до A5s»). По всему диапазону границу считать бессмысленно: «самая слабая рука вообще» не определена — непонятно, что слабее, 22 или 76s.

Тест проверяет инвариант на всех спотах: граница действительно играется, а всё, что ниже неё в ряду, — уже нет.

### Стол (`presets/scene.ts`, `ui/PokerTable.tsx`)

Спот показывается столом, а не строчкой текста: места по кругу, герой всегда внизу по центру, у каждого места позиция, стек и баттон у BU, чужие действия проигрываются **по очереди** (~0.5 с на решение, блайнды быстрее), фишки встают перед местами, банк считается на лету. После ответа над своим местом всплывает выбранное действие — зелёное, если чарт его играет, красное, если нет. Клик по столу пропускает анимацию, `prefers-reduced-motion` выключает её целиком.

`sceneFor(preset)` собирает сцену из чарта, и главное правило здесь то же, что в ветке событий: **не выдумывать данных.** Если чарт задан процентом («защита от 3бета 12%») или группой мест («vs ранние»), своей подписи у места нет — то, что о нём говорит чарт, остаётся в `note` («3бет 12%», «ранние»), и место помечается `exact: false` (подпись приглушена).

**Но стол при этом полный, и позиции у всех настоящие.** Игроки не исчезают оттого, что чарт не назвал их мест: за столом всегда шесть мест (кэш) или восемь (MTT), и это проверяется тестом. А раз стол полный, порядок посадки известен и блайнды сидят последними, то, посадив героя, мы знаем и всех остальных — поэтому позиция выводится из посадки (`finalize`: i-е место = i-я позиция), а не подписывается «?», как было раньше. Оттуда же берётся баттон.

Обратная сторона: **герой должен садиться внутрь своей группы.** Чарт «Ранние vs опен» с героем на HJ — это выведенная позиция, спорящая с подписью чарта. Поэтому у групповых MTT-чартов есть `MTT_HERO_SEAT` / `MTT_OPENER_SEAT` (ранние → EP+2 против EP+1, поздние → BU против CO), и тест сверяет группу с фактическим стулом героя.

Порядок показан так же честно: в чарте «3бет IP» блайнды сидят **позади** нас и к нашему решению ещё не ходили (мы же в позиции), а в защите от 3бета вне позиции они сдают уже **после** 3бета соперника — ход возвращается к нам последними. Часть MTT-чартов подписана просто «EP», без номера ранней позиции: перед таким героем садится ранний стул, иначе стол получился бы семиместным.

**Блайнды ставит `finalize`, а не билдер спота** — это правило стола, одинаковое везде. Пока каждый чарт выставлял их сам, в MTT-защите от 3бета их просто забыли, и заметно это стало только со стеками на столе. Тест требует ровно два блайнда, 0.5 и 1, у мест на SB и BB.

**Анте** — 1bb, только в MTT (`scene.ante`, у кэша 0). Это big blind ante: платит его один BB, поэтому у него списывается блайнд **и** анте, а в банке оно лежит ещё до первого решения — `potAfter` прибавляет его к нулевому шагу, а не проигрывает как ход. Под банком подписано «анте 1bb», иначе сумма не сходится с тем, что видно на столе.

**Стек** — общий для всех мест: у кэша 100bb, у MTT задан таблицей `MTT_STACK_BB` по подписи глубины. У открытых сверху берётся нижняя граница («25bb+» → 25), на ней чарт и начинает работать, а на коротких — рабочая часть диапазона: **8bb** на чарте 0-9bb и **12bb** на 10-14bb. Середина тут не годится: 4.5bb — это уже не спот, а формальность, пуш-фолд на таком стеке перестаёт быть выбором. У места показывается остаток, то есть за вычетом блайнда и анте.

Где чарт места называет — они настоящие: в защите блайндов от 4бета известен опенер, значит известны и все, кто сдал до него; неизвестно только, с какого из двух блайндов 3бетнули мы.

Сайзинги берутся из чарта, где они есть (`vs BU 2.5bb`), иначе — из правила Green Charts (CO/BU 2.5bb, остальные 3bb). Ставка не складывается с уже выставленным блайндом, а поднимается до суммы: «рейз до 3bb» с SB кладёт в банк 3bb, а не 3.5 (`potAfter`).

Лимпер в изолэйт-чартах — место прямо перед героем: конкретного лимпера чарт не называет, а ближайший стул хотя бы гарантированно успел походить.

Тесты держат сцены в рамках: герой за столом ровно один, все ходы принадлежат существующим местам, в банке всегда что-то есть, а последним перед нашим решением ходит **не** герой (свой ход в сцене бывает — опен перед 3бетом соперника, — но отвечаем мы всегда на чужой).

### Телефон

Тренажёр — единственная вкладка, которую реально открывают с телефона, поэтому вёрстка у него отдельная (`useIsCompact` в `ui/useMedia.ts`, брейкпоинт 640px — тот же `sm` у Tailwind).

**Стол на узком экране разворачивается вертикально**, как в мобильных покерных клиентах: пропорция 16:9 → 6:5 (кэш) или 4:5 (MTT, там по три места в боковой колонке), горизонтальный радиус меньше вертикального. Это не косметика: на 375px лежачий стол давал высоту 193px, места по бокам налезали друг на друга и на банк, а на 8-max SB просто скрывался за BB. Радиусы и пропорция считаются вместе — `tableShape()`; менять их порознь бессмысленно, места разъезжаются от их отношения.

Заодно в компактном режиме ужимаются карты, рубашки, облака действий и подписи: одной формы стола мало, места должны ещё и помещаться между собой. Подпись «(вы)» у героя убрана — его место и так подсвечено зелёным.

Список групп спотов на телефоне **свёрнут** (кнопка «Споты N/M»): он занимал пол-экрана над вопросом, хотя трогают его раз за сессию, а стол — каждую раздачу. На `sm` и выше он развёрнут всегда, тумблера нет.

Кнопки ответов на телефоне тянутся на всю ширину и держат высоту 44px (`min-h-11`) — это главное, чем в тренажёре тыкают пальцем.

Шапка приложения переносится по строкам: три вкладки рядом с названием в 375px не влезали, и «История рук» уезжала за край с горизонтальным скроллом всей страницы.

### Экспорт в Doyle Academy

MTT-чарты и тренажёр переиспользует «Doyle Academy» — раздел приложения покерного клуба (репозиторий `doyle timer`). Отдельного пакета нет, данные выгружаются скриптом:

```bash
npx vite-node tools/export_academy.ts              # пишет в ../doyle timer
npx vite-node tools/export_academy.ts --out=<путь> # или куда скажут
```

Кладёт два файла:

- `assets/academy/mtt-charts.json` — клиенту: матрицы, сцены спотов, кнопки ответов. Действия хранятся по отдельности (`actions[].w`), а не готовыми весами и сегментами заливки: обе производные клиент считает сам, иначе одни и те же числа ездили бы по мобильной сети трижды (344 КБ против 97).
- `supabase/migrations/academy_charts_seed.sql` — серверу: только «интересные» руки и суммарные веса по kind. Тренажёр в Академии **проверяет ответы на сервере** (там соревнование по стрику и таблица лидеров), поэтому чарт нужен в БД.

Скрипт не просто перекладывает данные, а **сверяет производные**: пересчитывает веса и границы ряда тем же способом, что клиентский `js/academy.js`, и сравнивает с `handWeights` / `actionEdges` из `quiz.ts` по всем 169 рукам каждого чарта (7098 сверок). Разойдутся — экспорт падает с ошибкой. Без этого Академия молча показывала бы разбор, не совпадающий с чартом, на отдельных руках.

Чарты для Академии берутся из секции `mtt` в `TRAINER_SECTIONS` — новая MTT-группа попадёт туда сама, отдельно в экспортёре её прописывать не нужно.

## История рук (`src/hh/`, `ui/Hands*.tsx`)

Вкладка «История рук»: импорт выгрузок GGPoker, HUD-статы, сверка префлопа с чартами и EV олл-инов. Аналог Hand2Note, только офлайн и в браузере.

### Формат GG и парсер

Диалект PokerStars. Три отличия, из-за которых чужой парсер не подходит:

- ники анонимизированы (hex), герой всегда `Hero`;
- в SUMMARY свои поля — `Jackpot / Bingo / Fortune / Tax`;
- **run-it-twice** размечен префиксами улиц: `*** FIRST FLOP ***`, `SECOND`, `THIRD`. Заголовок такой улицы содержит **весь борд этого раннинга**, поэтому борд собирается из самого заголовка, а не накоплением.

**Все суммы — целые центы.** На float «вложил ровно весь стек» не сходится, а на этом держится детект олл-ина.

**`raises $0.68 to $1.16` — первое число это надбавка над ставкой соперника, а не доложенные фишки.** Реально игрок кладёт `to` минус то, что у него уже стоит на улице. На этом парсер один раз уже ошибся: контрибуции не сходились с банком. Инвариант «сумма итогов всех игроков = −(рейк + джекпот)» проверяется тестом и держит эту ошибку.

Позиции выводятся **от места баттона**, а не от порядка ходов, и именуются назад от него (…UTG, MP, CO, BU) — на неполном столе пропадает UTG, а не CO. Если фактически выставленные блайнды не сошлись с вычисленными местами (вход в игру с пропущенным блайндом), раздача помечается `positionsReliable: false` и не идёт ни в разбивку по позициям, ни в сверку с чартами.

Валидировано на реальной выгрузке 2100 рук: денежный баланс сходится в каждой раздаче.

### Сверка с чартами

Каждое префлоп-решение героя отображается на конкретный чарт Green Charts, дальше берётся вес руки (`handWeights` из тренажёра) и сравнивается с сыгранным. Вердикты: `ok` / `mixed` (чарт играет так часть времени — не ошибка) / `loose` (сыграл то, чего в чарте нет) / `tight` (сфолдил то, что чарт всегда играет) / `action` (рука в чарте есть, но играется другим действием).

**%-чарты здесь подставляются по позиции — в отличие от ветки событий.** В `presets/tree.ts` чарты «3бет IP» и «защита от 3бета» выбираются вручную, потому что их процент — это ширина диапазона соперника. В истории рук соперник известен, поэтому берётся чарт, чей процент ближе всего к ширине, с которой этот соперник по Green Charts и играет. Подстановка не молчаливая: выбранный чарт и расчёт показываются в разборе («BB 3бетит 18.3% → чарт vs 3бет 18%, вне позиции»).

Лимпед-поты сверяются с чартом Isolate по месту героя. На BB там особый случай: отказаться от изолэйта можно только **чеком**, фолда в лимпед-поте у него нет, поэтому чек засчитывается как «не сыграл руку» (`checkDeclines` в `actionOf`). Без этого из выборки выпали бы все пропущенные изолэйты и «уже чарта» на BB не нашлось бы никогда.

3бет с блайнда, на который опенер ответил 4бетом, даёт **третье** решение раздачи и сверяется с чартом стр. 8 по месту 4бетора (у BU — ещё и по сайзингу его опена). Спот редкий: на выгрузке в 2100 рук он встретился 7 раз, так что проценты по нему пока ничего не значат.

Не покрыты чартами и честно считаются неразобранными: сквизы, 5бет+ и лимп с последующим рейзом до нас.

Сводка по спотам сортируется по **числу** отклонений, а не по доле: спот с одним решением и одной ошибкой даёт 100% и иначе занял бы первую строку.

### Разбор раздачи

Клик по строке в списке решений открывает `HandLogView`: частоты чарта для этой руки, граница по ряду (`actionEdges` из тренажёра — та же механика, что в подсказке при ошибке) и полный лог раздачи по улицам с подсветкой того самого хода.

Подсветка держится на `Decision.actionIndex` — индексе в `hand.actions`. Он нужен именно потому, что одна раздача может дать **два** решения (опен и ответ на 3бет), и без индекса непонятно, к какому из них относится вердикт. В `decisionsOf` индексы тащатся рядом с действиями, а не восстанавливаются поиском по игроку и типу: в раздаче с 4бетом герой рейзит дважды, и поиск нашёл бы не тот ход.

`log.ts` переводит суммы в **bb**: чарты, сайзинги и границы диапазонов живут в bb, и «рейз до 2.5bb» сразу сопоставим с подписью чарта. Итоги сортируются в порядке ходов постфлопа (SB, BB, UTG…), а не по номерам мест, — иначе они не совпадают с порядком в логе.

Клик по ячейке матрицы отбирает раздачи этой руки. Галка «только отклонения» снимается, чтобы посмотреть и решения по чарту.

### All-in EV

Считаются только **хедз-ап** олл-ины со вскрытием обоих: `equity × банк_без_рейка − вложенное`. Банк берётся как сумма `collected` — это уже за вычетом рейка, и при run-it-twice суммируется по раннингам, поэтому формула работает без отдельной ветки под RIT. Многовей требует разбора сайд-потов и в EV входит фактическим результатом (помечается `unsupported`).

Известный борд на момент олл-ина = min(улица последнего действия, общий префикс всех раннингов). Раннаут ≤ 3 карт перебирается точно, префлоп — Monte Carlo с ГПСЧ, **засеянным id раздачи**: цифра не пляшет между запусками, импорт идемпотентен.

Разбор считается один раз при импорте и хранится в поле `Hand.allIn` — иначе на каждой смене фильтра пересчитывались бы все префлоп-олл-ины.

### Хранилище

IndexedDB (`db.ts`), ключ — id раздачи с сайта, поэтому повторный импорт безопасен. Это важно: выгрузки GG пересекаются, каждая новая содержит и старые раздачи. localStorage не годится — лимит ~5 МБ это примерно 5 тысяч рук.

ZIP распаковывается своим кодом на `DecompressionStream("deflate-raw")` — библиотеку тянуть незачем. Читается **центральный каталог**, а не цепочка локальных заголовков: в локальном размеры могут быть нулями со ссылкой на data descriptor после данных.

Импорт целиком идёт в `hh.worker.ts`: распаковка + парсинг + эквити олл-инов на главном потоке подвесили бы интерфейс на секунды.

### Тесты

`fixtures.ts` — декларативный конструктор раздач (`makeHand({ hero: "CO", preflop: [...] })`). Простыни текста истории разбираются только в `parse.test.ts` на реальных выгрузках; тест про 3бет не должен падать из-за опечатки в строке рейка.

## Статус

MVP готов целиком: матрица с покраской и весами, борд с пикером, MADE-разбивка с дро, эквити range vs range в воркере, морфинг диапазона по категориям, heatmap, сохранение сценариев в localStorage, префлоп-чарты за веткой событий с раскраской по действиям, тренажёр по префлопу, импорт истории рук GG со статами, сверкой с чартами и EV олл-инов.

MTT-пак FF START оцифрован целиком: 42 чарта на семи группах, своя ветка событий с выбором глубины стека, тренажёр и раскраска по действиям работают на них так же, как на кэшевых.

Возможные направления дальше: экспорт/импорт диапазонов строкой для шаринга; именованные слоты сохранения; мультивей (3+ игрока); графики распределения эквити; в тренажёре — показ чарта после ответа и статистика ошибок по рукам. По истории рук: реплеер раздачи, фильтры по датам и стейкам, статы на соперников (сейчас разбирается только герой), постфлоп-сверка.
