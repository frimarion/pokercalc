# PokerCalc

Веб-приложение: свой аналог **Flopzilla** с расширенным функционалом. Всё считается в браузере, бэкенда нет.

Референс по UI и фичам — софт «Greenline Junior» (тёмная тема, матрица 13×13, разбор борда по категориям, эквити, heatmap).

Ключевые фичи, ради которых проект и строится: **эквити range vs range** и **range morphing** (сужение диапазона по улицам).

## Команды

```bash
npm run dev        # дев-сервер → http://localhost:5173
npm test           # vitest
npm run typecheck  # tsc без сборки
npm run build      # прод-сборка
```

Терминал с `npm run dev` держать открытым — это и есть сервер.

## Стек

Vite 6 + React 19 + TypeScript + Tailwind v4 + Zustand. Тесты — Vitest. Эквити считается в Web Worker.

### Модель диапазона

`Range` — `Float32Array` на 1326 комбо, вес каждого 0..1. Мутируется на месте, поэтому в сторе есть счётчик `rev`, который инкрементится при любом изменении — на него подписаны компоненты, иначе React не перерисует.

Блокеры (карты борда и heroCards) — bigint-маска; `liveCombos(mask)` и `totalCombos(mask)` отсекают пересекающиеся комбо.

### Эквити

`computeEquity(a, b, board, opts)` — гибрид: если пространство раскладов маленькое (обычно тёрн/ривер), идёт точный перебор, иначе Monte Carlo. Валидировано по эталонам: AA vs KK ≈ 82%, AKs vs QQ ≈ 46%.

Hero-сторона в UI: если заданы **обе** карты в слотах Hero — считается эта конкретная рука; иначе берётся диапазон Hero.

## Префлоп-пресеты (Green Charts 2024, Greenline Poker)

Источник — PDF `~/Downloads/GreenCharts2024_01.pdf`, 12 страниц, кэш NL2–NL200. Диапазоны **оцифрованы скриптом**, не набраны руками.

### Модель — по действиям

```ts
RangePreset {
  actions: PresetAction[]   // kind: "raise" | "call"
}
PresetAction {
  always: string[], situational: string[],
  threeQuarter?: string[], quarter?: string[],   // только Defense vs 3Bet
  color?: ActionColor, label: string,            // для легенды и раскраски
}
```

- `always` → вес **1.0** (в чарте сплошной цвет)
- `situational` → вес **0.5**
- `threeQuarter` / `quarter` → **0.75** / **0.25**

Полсотни процентов — не выдумка: подписанные в PDF проценты сходятся **только** по формуле `always + situational/2`. Это проверяется тестом. Четверти понадобились только на стр. 10–11, где ячейка делится не пополам.

Одному `kind: "raise"` могут отвечать **два** действия с разным `color` — так в Defense vs 3Bet разделены «4бет-фолд» (красный) и «4бет-пуш» (фиолетовый). На вес и на фильтр действия это не влияет, нужно только для легенды.

`store.applyPreset(id, includeSituational, actionKind?)` — без `actionKind` применяются все действия пресета, и руки, лежащие в двух действиях по половине, складываются в полный вес.

### Семантика цветов зависит от типа чарта — легенду смотреть каждый раз

| Страница | Чарт | Красный | Жёлтый / Зелёный |
|---|---|---|---|
| 4 | RFI | открываем всегда | жёлтый — ситуативно |
| 6 | SB Defense | 3бетим всегда | жёлтый — 3бетим в подходящих оппонентов |
| 7 | BB Defense | 3бетим | **зелёный — коллируем** |
| 5 | Isolate | открываем изолэйтом | **зелёный — доставляем 0.5bb на SB** |

На SB — чистый 3бет-или-фолд, флэтов нет. На BB есть и колл, поэтому там два действия.

**Составные ячейки:** в BB-чартах ячейка может быть закрашена наполовину двумя цветами — смешанная стратегия «половину раздач 3бет, половину колл», всегда ровно 50/50. Такие руки попадают в `situational` **обоих** действий.

### Что уже оцифровано

- `rfi.ts` — стр. 4: UTG 14%, MP 16%, CO 26%, BU 42%, SB 44%. Сайзинг CO/BU 2.5bb, остальные 3bb.
- `iso.ts` — стр. 5: изолэйт после лимпа, MP 11% / CO 14% / BU 20% / SB 12% / BB 14%. Генерируется `tools/gen_iso.py`.
- `sbDefense.ts` — стр. 6: vs UTG / MP / CO / BU
- `bbDefense.ts` — стр. 7: vs UTG / MP / CO / SB, плюс vs BU отдельно для сайзингов 2.5bb и 3bb
- `threeBetIP.ts` — стр. 9: 3бет в позиции vs опен 15% / 18% / 26%
- `defenseVs3bet.ts` — стр. 10 и 11: защита от 3бета в позиции (6/8/10/12/14%) и без позиции (8/10/12/18%)

**Осторожно с процентами.** `extract_charts.py` печатает `total` как долю **закрашенной площади** чарта (жёлтый считается за целую руку), а эффективная ширина диапазона в приложении — это `always + situational/2`. Для RFI UTG это 16.0% против 14.1%. Сверять надо с эффективной: её считает `presetWidthPct()` в `presets/tree.ts`, она же показывается под веткой событий.

### Осталось оцифровать

Стр. 8 Blinds vs 4bet.

### Как оцифровывать (процедура)

Требуется `pip install PyMuPDF numpy scipy`.

1. `python tools/extract_charts.py <номер_страницы>` — для чартов без составных ячеек.
   `python tools/extract_charts_mixed.py <номер_страницы>` — если в чарте есть ячейки, закрашенные двумя цветами (считает доли пикселей).
2. Посмотреть легенду страницы: отрендерить верхнюю полосу (`clip` в fitz) — от неё зависит смысл цветов и структура действий.
3. Сетки сортируются «сверху вниз, слева направо»; подписи (какая позиция против какой) скрипт не знает — берутся из легенды/скриншота.
4. **TS-файл генерировать скриптом на Python**, а не набирать руками. При ручном переносе уже была поймана реальная опечатка (дубль `A6o` в RFI BU).
5. Если всё же правил руками — сверить регуляркой с извлечённым JSON перед коммитом.

### Изолэйт (стр. 5)

Легенда: красный — открытие изолэйтом, зелёный — «доставляем 0,5bb на SB, если до нас уже были лимперы». Зелёный есть **только** в чарте SB: доставить блайнд может лишь тот, кто его уже наполовину поставил. UTG в чарте нет — до него лимпить некому.

Сайзинг: в позиции 4bb + 1bb за каждого лимпера, без позиции 5bb + 1bb. По этому признаку CO/BU считаются в позиции, MP/SB/BB — вне.

Составные ячейки здесь ровно 50/50 и это **настоящий раздел ячейки**, а не другой цвет чернил, как жёлтый в RFI, — поэтому ISO не входит в `YELLOW_PARTIAL_GROUPS` в `store.ts`. Подписанный на чарте процент относится к **красному** диапазону: у SB это 12% при зелёных 17.9% сверху.

Проверка сходимости при оцифровке (доли пикселей → вес 0.5 на половинках): MP 10.7 против подписанных 11, CO 14.1 против 14, BU 20.1 против 20, SB-изо 12.1 против 12, BB 13.7 против 14.

Половинные ячейки читаются как 0.41–0.54, а не ровно 0.5: тёмный текст ярлыка внутри ячейки съедает часть пикселей, сильнее всего в offsuit-ячейках с тремя символами. Порог в `gen_iso.py` поэтому низкий (0.06), но заведомо выше шума антиалиасинга.

## Гочи

- **vitest тянет свою вложенную копию vite** → конфликт типов. Поэтому конфиги разделены: `vite.config.ts` (плагины, без `test`) и отдельный `vitest.config.ts` (только `test`).
- **localhost на Windows** может резолвиться в IPv6 (`::1`), а Vite слушать IPv4 → `ERR_CONNECTION_REFUSED`. В `vite.config.ts` стоит `server.host: true` и фиксированный порт 5173.
- Извлечение чартов: заголовок чарта слипается с сеткой при дилатации маски — границы берутся по **span** строк/столбцов с плотностью > 0.6, а не по «самому длинному непрерывному участку» (последний рвётся на 13 кусков из-за белых зазоров между рядами ячеек).
- Сетки одного ряда могут отличаться по `y` на пиксель, поэтому сортировка идёт по `(round(y/400), x)`.

## Цвета матрицы

Тип руки задаёт оттенок, вес — насыщенность (`src/ui/colors.ts`):

- пары (диагональ) — зелёный
- suited (верхний треугольник) — синий
- offsuit (нижний треугольник) — оранжевый

Heatmap (тумблер в боковой панели) перекрашивает руки диапазона по силе на борде: красный слабо → зелёный сильно.

**Цвета пресета** (тумблер там же) красит руки по действию, как в оригинальных чартах: зелёный — колл, красный — 3бет / 4бет-фолд, фиолетовый — 4бет-пуш, жёлтый — ситуативные руки в RFI/SB/3бет-IP. Составная ячейка заливается сегментами пропорционально весам. Раскладка живёт в `store.presetView`, подписи легенды — в `store.presetLegend` (берутся из `action.label`, поэтому легенда всегда соответствует текущему чарту). Любая ручная правка диапазона обнуляет и то, и другое — раскраска по действиям после неё уже не имеет смысла.

## Ветка событий (`ui/ActionTree.tsx`, `presets/tree.ts`)

Спот собирается по шагам, как action tree в GTO Wizard: **кто открыл → кто и как ответил → как опенер ответил на 3бет**. Плоских рядов кнопок по группам больше нет.

- Кто IP, а кто OOP, выводится строго из мест за столом: 3бет от CO/BU оставляет опенера **вне** позиции, 3бет от блайндов — **в** позиции, а BB против опена SB сам оказывается в позиции (это и есть чарт «OOP vs 3bet 18% (SB vs BB)»).
- Чарты, заданные **процентом** (3бет IP, защита от 3бета), по позиции **не** подставляются: проценты в них — ширина диапазона соперника, и с нашими позиционными диапазонами они совпадают лишь приблизительно. Такой шаг даёт явный выбор %, а фактическая ширина показана подсказкой.
- `presetForPath(path)` — какой чарт и фильтр действия соответствуют пути. Тест обходит всё дерево и проверяет, что каждый `presetId` существует и в чарте есть указанное действие.

## Тренажёр (`ui/Trainer.tsx`, `presets/quiz.ts`)

Вкладка «Тренажёр» в шапке. Показывает конкретную руку в конкретном споте, игрок выбирает действие, дальше — разбор с долями по чарту.

**Очевидные вопросы не задаются.** Спрашивать «открываем ли 72o с UTG» бессмысленно. В выборку (`interestingHands`) попадают только:

1. **смешанные** руки — чарт играет их частично (0.25/0.5/0.75), правильных ответов несколько;
2. **пограничные** — соседняя по сетке рука играется иначе (A5s открываем, A4s уже нет → обе в тесте).

Всё, что окружено такими же руками с тем же действием, отсеивается: и мусор, и премиум в середине своей зоны. Из 169 ярлыков остаётся ~55–90 на спот. Это закреплено тестами (`72o`/`AA` для RFI UTG в выборку попадать не должны).

Соседство считается по сетке 13×13, но переходы пара↔непара соседством **не** считаются (у них разная природа), а `suited↔offsuit` той же пары рангов — считается: AJs играем, AJo нет — полезная граница.

Ответ верен, если чарт играет руку так **хоть какую-то долю времени** (`isCorrect`): на смешанной руке верны оба действия, фолд — нет.

Действия одного `kind` при проверке складываются: «4бет-фолд» и «4бет-пуш» для игрока — один ответ «4бет», разделены они только ради цвета в легенде.

**Подсказка о границе.** При неверном ответе показывается, докуда тянется каждое действие (`actionEdges`): «Граница среди Axs: колл — до A2s, 3бет — до A4s (частично)».

Граница считается по **ряду** руки в матрице (`handFamily`) — те же старшая карта и тип: для AJs это все Axs, для AJo — Axo, для 77 — все пары. Именно так чарты и запоминаются («Axs открываем до A5s»). По всему диапазону границу считать бессмысленно: «самая слабая рука вообще» не определена — непонятно, что слабее, 22 или 76s.

Тест проверяет инвариант на всех спотах: граница действительно играется, а всё, что ниже неё в ряду, — уже нет.

## История рук (`src/hh/`, `ui/Hands*.tsx`)

Вкладка «История рук»: импорт выгрузок GGPoker, HUD-статы, сверка префлопа с чартами и EV олл-инов. Аналог Hand2Note, только офлайн и в браузере.

### Формат GG и парсер

Диалект PokerStars. Три отличия, из-за которых чужой парсер не подходит:

- ники анонимизированы (hex), герой всегда `Hero`;
- в SUMMARY свои поля — `Jackpot / Bingo / Fortune / Tax`;
- **run-it-twice** размечен префиксами улиц: `*** FIRST FLOP ***`, `SECOND`, `THIRD`. Заголовок такой улицы содержит **весь борд этого раннинга**, поэтому борд собирается из самого заголовка, а не накоплением.

**Все суммы — целые центы.** На float «вложил ровно весь стек» не сходится, а на этом держится детект олл-ина.

**`raises $0.68 to $1.16` — первое число это надбавка над ставкой соперника, а не доложенные фишки.** Реально игрок кладёт `to` минус то, что у него уже стоит на улице. На этом парсер один раз уже ошибся: контрибуции не сходились с банком. Инвариант «сумма итогов всех игроков = −(рейк + джекпот)» проверяется тестом и держит эту ошибку.

Позиции выводятся **от места баттона**, а не от порядка ходов, и именуются назад от него (…UTG, MP, CO, BU) — на неполном столе пропадает UTG, а не CO. Если фактически выставленные блайнды не сошлись с вычисленными местами (вход в игру с пропущенным блайндом), раздача помечается `positionsReliable: false` и не идёт ни в разбивку по позициям, ни в сверку с чартами.

Валидировано на реальной выгрузке 2100 рук: денежный баланс сходится в каждой раздаче.

### Сверка с чартами

Каждое префлоп-решение героя отображается на конкретный чарт Green Charts, дальше берётся вес руки (`handWeights` из тренажёра) и сравнивается с сыгранным. Вердикты: `ok` / `mixed` (чарт играет так часть времени — не ошибка) / `loose` (сыграл то, чего в чарте нет) / `tight` (сфолдил то, что чарт всегда играет) / `action` (рука в чарте есть, но играется другим действием).

**%-чарты здесь подставляются по позиции — в отличие от ветки событий.** В `presets/tree.ts` чарты «3бет IP» и «защита от 3бета» выбираются вручную, потому что их процент — это ширина диапазона соперника. В истории рук соперник известен, поэтому берётся чарт, чей процент ближе всего к ширине, с которой этот соперник по Green Charts и играет. Подстановка не молчаливая: выбранный чарт и расчёт показываются в разборе («BB 3бетит 18.3% → чарт vs 3бет 18%, вне позиции»).

Лимпед-поты сверяются с чартом Isolate по месту героя. На BB там особый случай: отказаться от изолэйта можно только **чеком**, фолда в лимпед-поте у него нет, поэтому чек засчитывается как «не сыграл руку» (`checkDeclines` в `actionOf`). Без этого из выборки выпали бы все пропущенные изолэйты и «уже чарта» на BB не нашлось бы никогда.

Не покрыты чартами и честно считаются неразобранными: сквизы, 4бет+ и лимп с последующим рейзом до нас.

Сводка по спотам сортируется по **числу** отклонений, а не по доле: спот с одним решением и одной ошибкой даёт 100% и иначе занял бы первую строку.

### Разбор раздачи

Клик по строке в списке решений открывает `HandLogView`: частоты чарта для этой руки, граница по ряду (`actionEdges` из тренажёра — та же механика, что в подсказке при ошибке) и полный лог раздачи по улицам с подсветкой того самого хода.

Подсветка держится на `Decision.actionIndex` — индексе в `hand.actions`. Он нужен именно потому, что одна раздача может дать **два** решения (опен и ответ на 3бет), и без индекса непонятно, к какому из них относится вердикт. В `decisionsOf` индексы тащатся рядом с действиями, а не восстанавливаются поиском по игроку и типу: в раздаче с 4бетом герой рейзит дважды, и поиск нашёл бы не тот ход.

`log.ts` переводит суммы в **bb**: чарты, сайзинги и границы диапазонов живут в bb, и «рейз до 2.5bb» сразу сопоставим с подписью чарта. Итоги сортируются в порядке ходов постфлопа (SB, BB, UTG…), а не по номерам мест, — иначе они не совпадают с порядком в логе.

Клик по ячейке матрицы отбирает раздачи этой руки. Галка «только отклонения» снимается, чтобы посмотреть и решения по чарту.

### All-in EV

Считаются только **хедз-ап** олл-ины со вскрытием обоих: `equity × банк_без_рейка − вложенное`. Банк берётся как сумма `collected` — это уже за вычетом рейка, и при run-it-twice суммируется по раннингам, поэтому формула работает без отдельной ветки под RIT. Многовей требует разбора сайд-потов и в EV входит фактическим результатом (помечается `unsupported`).

Известный борд на момент олл-ина = min(улица последнего действия, общий префикс всех раннингов). Раннаут ≤ 3 карт перебирается точно, префлоп — Monte Carlo с ГПСЧ, **засеянным id раздачи**: цифра не пляшет между запусками, импорт идемпотентен.

Разбор считается один раз при импорте и хранится в поле `Hand.allIn` — иначе на каждой смене фильтра пересчитывались бы все префлоп-олл-ины.

### Хранилище

IndexedDB (`db.ts`), ключ — id раздачи с сайта, поэтому повторный импорт безопасен. Это важно: выгрузки GG пересекаются, каждая новая содержит и старые раздачи. localStorage не годится — лимит ~5 МБ это примерно 5 тысяч рук.

ZIP распаковывается своим кодом на `DecompressionStream("deflate-raw")` — библиотеку тянуть незачем. Читается **центральный каталог**, а не цепочка локальных заголовков: в локальном размеры могут быть нулями со ссылкой на data descriptor после данных.

Импорт целиком идёт в `hh.worker.ts`: распаковка + парсинг + эквити олл-инов на главном потоке подвесили бы интерфейс на секунды.

### Тесты

`fixtures.ts` — декларативный конструктор раздач (`makeHand({ hero: "CO", preflop: [...] })`). Простыни текста истории разбираются только в `parse.test.ts` на реальных выгрузках; тест про 3бет не должен падать из-за опечатки в строке рейка.

## Статус

MVP готов целиком: матрица с покраской и весами, борд с пикером, MADE-разбивка с дро, эквити range vs range в воркере, морфинг диапазона по категориям, heatmap, сохранение сценариев в localStorage, префлоп-чарты за веткой событий с раскраской по действиям, тренажёр по префлопу, импорт истории рук GG со статами, сверкой с чартами и EV олл-инов.

Возможные направления дальше: оцифровать стр. 5 и 8; экспорт/импорт диапазонов строкой для шаринга; именованные слоты сохранения; мультивей (3+ игрока); графики распределения эквити; в тренажёре — показ чарта после ответа и статистика ошибок по рукам. По истории рук: реплеер раздачи, фильтры по датам и стейкам, статы на соперников (сейчас разбирается только герой), постфлоп-сверка.
